# subsystems/claude-team

Équipe d'agents Claude Code générée depuis un manifeste, avec boucle
d'amélioration mesurée. Module Nebula `claude-team` (overlay), posé
par-dessus `claude-self-improving` (requis).

## Manifeste `.claude/team.json`

Source de vérité du module dans ce workspace. Sections : `team`
(nom, version, point d'entrée, **`prefix`**), `models` (alias `sonnet` /
`opus`, `default`), `capabilities_catalog`, `agents` (7 entrées), et
`improvement_loop` (paramètres de la boucle, cf.
[`conventions/improvement-loop.md`](../conventions/improvement-loop.md)).

Les corps des agents vivent dans `.claude/team/agents/<id>.md` (sans
frontmatter). C'est là qu'on édite un prompt.

## Préfixe des agents générés

`team.prefix` : choisi dans la modale d'activation de Nebula (champ
« Préfixe des agents », défaut = id du workspace, règle
`^[a-zA-Z0-9_-]{1,40}$`), écrit dans la copie workspace du manifeste par
le générateur, relu par les régénérations suivantes si la modale ne le
fournit pas. Exemple : `dash` donne `dash-orchestrator` à côté de
`dash-expert`. Seuls les agents **générés** portent le préfixe : les
corps sources, les commandes et le bloc `CLAUDE.md` parlent des agents
par `<préfixe>-<id>`, et la règle « Délégation » en tête de chaque agent
généré donne les noms exacts.

## Génération des agents

À l'activation du module (et à chaque ré-application), Nebula génère
`.claude/agents/<préfixe>-<id>.md` pour chaque agent du manifeste, avec
un frontmatter Claude Code valide. Idempotent : un agent déjà présent
n'est pas écrasé ; l'option « Régénérer les agents générés par Nebula »
ne réécrit que les fichiers dont le corps commence par le marqueur
`<!-- generated by nebula claude-team -->`. Un agent sans ce marqueur
(édité à la main, ou créé par l'utilisateur) n'est jamais touché.

### Mapping manifeste -> frontmatter

| Manifeste | Frontmatter généré |
|---|---|
| `id` | `name: <préfixe>-<id>` |
| `description` | `description` + rôle + coût typique si connu |
| `model` (clé de `models`) | `model: sonnet` / `opus` (overridable par workspace à l'activation : `models`, `default_model`, `haiku` accepté) |
| `capabilities` + `read_only` | `tools` : `filesystem` -> Read, Glob, Grep (+ Edit, Write si non read_only) ; `code_exec` -> Bash ; `repo` -> Bash ; `web_search` -> WebSearch, WebFetch ; `knowledge` -> Read, Grep ; `eval_runner` -> Bash, Read ; point d'entrée (`team.entrypoint`) -> + Agent |
| `can_delegate_to` | Règle « Délégation » dans le corps, avec les noms générés réels (préfixe inclus) |
| `max_turns`, `isolation`, `escalate_to`, `temperature`, `scope` | Bloc « Contraintes d'exécution » en tête du corps (pas d'équivalent natif) |

`{{name}}` vaut le préfixe dans les agents générés, l'id du workspace
dans les autres fichiers copiés (commandes, mémoire, fragment) ;
`{{label}}` est substitué partout.

## Les 7 agents

| Agent | Modèle | Rôle |
|---|---|---|
| `<préfixe>-orchestrator` | opus | Découpe, délègue, assemble. En temps normal, ce rôle est joué par le **fil principal** via `/team` ; l'agent sert à la délégation explicite |
| `<préfixe>-researcher` | sonnet | Faits sourcés, lecture seule |
| `<préfixe>-architect` | opus | Plan d'implémentation, lecture seule |
| `<préfixe>-executor` | sonnet (escalade opus) | Implémente le plan : tâches S, étapes atomiques |
| `<préfixe>-reviewer` | opus | Relecture à froid, isolation blind |
| `<préfixe>-evaluator` | sonnet | **Note en aveugle** (sortie + attendu + grille), n'exécute rien |
| `<préfixe>-critic` | opus | UN diff par itération, boucle uniquement |

## Cohabitation avec le module Auto-amélioration

Si `.claude/agents/` contient un agent `*-expert`, c'est lui l'exécutant
des tâches conséquentes (feature M+, 10 fichiers ou plus,
multi-domaines, refactor à effets de bord) : il porte la mémoire projet.
`<préfixe>-executor` reste l'exécutant des tâches S et des étapes
atomiques d'un plan. Si `*-impl-validator` existe, il complète
`<préfixe>-reviewer` (après lui, jamais à sa place). Les deux blocs
always-on de `CLAUDE.md` (Auto-amélioration, Équipe) se lisent ainsi
sans conflit.

## Routage always-on (trois couches)

L'utilisateur parle normalement ; le fil principal route vers l'équipe
sans appel explicite et rend une réponse unique, sourcée et relue. Tout
se lit dans `.claude/team.json`, rien n'est régénéré pour changer de mode.

| Couche | Où | Quoi |
|---|---|---|
| 1. Table | `CLAUDE.md` § « Routage automatique (always-on) » | question -> `<préfixe>-researcher` (sonnet, sources `fichier:ligne`) ; conception -> `<préfixe>-architect` (opus) ; tâche S -> `<préfixe>-executor` puis relecture aveugle `<préfixe>-reviewer` ; M+ -> `*-expert` puis reviewer puis `*-impl-validator` ; relecture -> reviewer ; ambigu / multi-étapes -> `/team` ; jamais critic ni evaluator. Règles : gate reviewer, sortie unifiée (pied `équipe : ...`), budget sonnet-first |
| 2. Déclencheurs | `team.json` : `routing` + `auto` / `triggers` par agent ; description générée | « À utiliser automatiquement quand : <déclencheurs> » (`auto: true`) ou « Jamais en routage automatique : réservé à /eval et /improve » (`auto: false`) ; ligne « Routage » dans les contraintes. Claude Code lit la description pour déléguer de lui-même |
| 3. Hook | `.claude/hooks/team-router.py` (UserPromptSubmit, sans matcher) | classe le prompt (question / conception / implementation / relecture / inconnu) et injecte une ligne `[équipe claude-team] routage auto : ...` (JSON `hookSpecificOutput.additionalContext`) ; `suggestion : ...` en `assiste` ; silencieux en `manuel`, sans section `routing`, sur une slash command |

`routing.mode` : `manuel` / `assiste` / `auto` (défaut `auto`) ;
`routing.review_gate` : `always` (défaut) / `from_3_files` / `never` ;
`routing.budget` : `sonnet-first`. Changement depuis Nebula (onglet
Configuration, ligne du module : sélecteurs « Routage » et « Relecture du
code », pill d'état) ou `POST /api/workspaces/<id>/team/routing`. Un
manifeste sans section `routing` (activé avant) = mode effectif `manuel`,
pill « Routage non déclaré », bouton « Activer le routage » qui écrit la
section par défaut.

## Hooks et commandes

- `.claude/hooks/evals-lock.py` (PreToolUse `Edit|Write|MultiEdit` et
  `Bash`, câblé par le module dans `.claude/settings.json`) : refuse toute
  écriture sous `.claude/evals/` tant que `eval_set_locked` est vrai,
  sauf `"evals_unlocked": true` dans `.claude/settings.local.json`.
- `.claude/hooks/team-router.py` (UserPromptSubmit) : routage
  déterministe, cf. ci-dessus. Fail-open (fichier absent ou illisible =
  exit 0 sans sortie), stdlib, UTF-8 explicite.
- `/team <objectif>` : orchestration complète par le fil principal ; en
  `auto`, voie des demandes multi-étapes.
- `/eval [--tag] [--agent] [--id]` : le fil principal boucle sur les
  cas, délègue chaque `input` à l'agent visé, note `test` / `regex` /
  `exact` lui-même, fait noter `rubric` en aveugle. `config_version` =
  empreinte manifeste + corps + agents générés (one-liner de la
  commande, même algorithme que Nebula).
- `/improve [N]` : itérations de la boucle ; baseline du journal
  réutilisée si l'empreinte est inchangée et sans cas inexécutable ;
  commit des itérations acceptées (demande explicite portée par la
  commande), jamais de push.
- `/eval-add` : nouveau cas depuis un échec observé (schéma : `agent`,
  `grader`, `check`, `target`, `scope`, `runs`).

## Vue Nebula

Ligne du module « Équipe d'agents » (onglet Configuration du workspace) :
routage, relecture, modèle et effort par agent (dépliable « Régler »),
badge « N agent(s) à régénérer » et bouton « Régénérer » quand un corps
d'agent a changé. Nebula ne lance aucune itération d'amélioration.
L'équipe s'améliore au fil des conversations (règle « Amélioration au fil
des conversations » du `CLAUDE.md`) ; `/eval` et `/improve` restent
manuels. Données : `GET /api/workspaces/<id>/team` (`prefix`,
`config_hash`).
